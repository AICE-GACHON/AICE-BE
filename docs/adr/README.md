# ADR (Architecture Decision Record)

**여기부터는 새 설계 결정을 결정 하나당 파일 하나로 기록합니다.** 기존
[AI_파트_설계서.md](../AI_파트_설계서.md)는 §1~26을 끝으로 동결됐습니다 — 계속
append하는 단일 파일 방식이 실제로 섹션 번호 충돌 사고(§20/§21)를 냈기 때문입니다.
새 ADR은 파일이 독립적이라 번호가 겹칠 일이 없고, 결정 하나의 맥락(왜·무엇을·
무엇과 비교했는지)이 한 파일 안에서 끝납니다.

## 언제 ADR을 쓰는가

되돌리기 번거롭거나, 나중에 "왜 이렇게 했더라"를 물을 만한 결정일 때만 씁니다.
버그 수정이나 리팩터링에는 필요 없습니다 — 예를 들면:

- 파이프라인 단계·모델·알고리즘을 바꾸는 결정 (예: 검색 랭킹 가중치, 재정렬 모델 선택)
- 스키마·API 계약을 바꾸는 결정 (특히 되돌리기 비싼 것)
- 여러 대안을 실측/비교해서 하나를 고른 결정
- "왜 이렇게 안 했는가"가 나중에 또 나올 만한 결정 (실패한 접근 기록)

일상적인 버그 수정, 리팩터링, 오타 수정에는 필요 없습니다 — 커밋 메시지로 충분합니다.

## 파일 이름

```
docs/adr/NNNN-짧은-제목.md
```

`NNNN`은 4자리 순번(0001, 0002, ...)이고, 한 번 부여되면 그 번호는 상태가 바뀌어도
(예: 나중에 다른 결정이 이걸 대체해도) 재사용하지 않습니다. 제목은 결정의 결과를
짧게 요약합니다(예: `0001-rerank-model-sonnet.md`).

## 템플릿

```markdown
# NNNN. 짧은 제목

- 날짜: YYYY-MM-DD
- 상태: 제안됨 | 채택됨 | 대체됨(→ NNNN) | 폐기됨

## 문제

무엇을 결정해야 했는가. 왜 지금 결정해야 했는가.

## 검토한 대안

각 대안과 왜 안 골랐는지 (실측이 있으면 수치와 함께).

## 결정

무엇을 골랐는가. 한두 문단으로 충분합니다.

## 근거

왜 이게 맞다고 판단했는가. 실측·트레이드오프·제약.

## 결과

이 결정으로 무엇이 바뀌는가 (코드·API·운영). 되돌리려면 무엇을 해야 하는가.
```

`상태`가 `대체됨`이 되면 새 ADR 파일을 만들고 여기에 화살표로 연결합니다 — 기존
파일을 고쳐 쓰지 않습니다. ADR은 그 결정을 내린 시점의 기록이라 append-only입니다.
