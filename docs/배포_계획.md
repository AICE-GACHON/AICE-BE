## 0. 목표와 범위

**소수 실사용자 베타.** 초대한 사람들이 실제로 논문을 올리고 분석을 돌립니다.

이 한 줄이 아래 기준선을 전부 결정합니다.

| | 이번 범위 | 이번 범위가 **아닌** 것 |
|---|---|---|
| 가용성 | 단일 인스턴스. 배포·재부팅 시 수 분 다운타임 허용 | 무중단 배포, 다중 AZ, 오토스케일 |
| 데이터 | **유실은 안 됨.** 자동 백업 + 시점 복구 필수 | 지역 간 이중화 |
| 부하 | 동시 분석 1~2건 | 워커 확장, 큐 분리 |
| 비용 | AWS 신규 가입 크레딧 $200 안에서 | 장기 운영 최적화 |

"데모용"이 아니라 "베타"인 것이 백업 요구를 만들고, 그게 뒤에서 RDS 선택으로
이어집니다. "운영 서비스"가 아닌 것이 `BackgroundTasks`를 그대로 두는 근거입니다.

## 1. 코드에서 확인한 제약

배포 방식을 고르기 전에 **저장소가 이미 정해놓은 것**들입니다. 전부 실측이거나
파일 참조입니다 — 추측이 아닙니다.

### 1.1 스테이트풀한 것은 Postgres 하나뿐. 대신 무겁다

측정 시점(2026-08-07) 로컬 개발 DB 기준:

| | 크기 |
|---|---|
| 데이터베이스 전체 | **1,452 MB** |
| `papers` | 586 MB |
| `reviews` | 435 MB |
| `review_points` | 389 MB |
| 나머지 (authors, submissions, ...) | ~40 MB |
| `data/export/paper_assistant.dump` | **459 MB** |

논문 43,515편 / 리뷰 168,217건 / 지적항목 119만 건.

- **pgvector + HNSW가 필수**입니다. `papers.embedding`이 `vector(768)`
  ([scripts/init_db.sql:39](../scripts/init_db.sql)). 아무 PostgreSQL이나 쓸 수 없습니다.
- **업로드 PDF도 DB에 들어갑니다.** `submissions.pdf_bytes`가 BYTEA
  ([app/models/submission.py:45](../app/models/submission.py), alembic 0011).
  별도 파일 스토리지가 필요 없는 대신 **DB가 사용자 활동만큼 계속 커집니다** —
  1건당 최대 20 MB. 베타 규모에선 문제없지만 스토리지 사이징에 여유를 둡니다.

### 1.2 RAM이 병목이다 (CPU가 아니라)

SPECTER2(`allenai/specter2_base` + adapter, BERT-base 768차원)를 torch CPU로
**API 프로세스 안에서** 돌립니다 ([paper_assistant/embedding/specter2.py](../paper_assistant/embedding/specter2.py)).

**실측 (2026-08-07, 빌드한 배포 이미지 안에서).** 처음에는 2~2.5 GB로 추정했지만,
재보니 그보다 작습니다.

| 시점 | RSS |
|---|---|
| 프로세스 기동 직후 | 9 MB |
| torch·adapters import 후 | 325 MB |
| SPECTER2 로드 직후 | 353 MB |
| **임베딩 1건 추론 후** | **703 MB** |
| 배치 64건 후 | 722 MB |

🔴 **로드 직후(353 MB)와 첫 추론 후(703 MB)의 차이에 주의하세요.** safetensors가
가중치를 mmap하기 때문에 **로드만으로는 페이지가 올라오지 않고, 추론이 건드릴 때
올라옵니다.** "모델을 올렸으니 됐다"며 기동 직후 메모리만 보면 실제 사용량을
절반으로 잘못 봅니다 — 실제로 워밍업만 끝난 uvicorn 프로세스는 435 MB였습니다.

⚠️ **아직 재지 않은 것이 있습니다.** 위 숫자는 임베딩 경로만입니다. 실제 분석은
그 위에 PDF 처리(PyMuPDF, 최대 20 MB·60페이지, **스캔본은 페이지를 이미지로
렌더링**), LangGraph 상태, LLM 호출용 PDF 바이트가 더 얹힙니다. **스캔본 렌더링이
가장 큰 미지수**입니다.

- 실제 API 프로세스는 **1~1.5 GB** 대로 보이지만 위 미지수가 남아 있습니다
- → **API만 두는 D4의 t4g.medium(4 GB)은 여유가 있습니다.** 다만 DB까지 같은 박스에
  넣는 구성은 페이지 캐시로 1.45 GB를 더 원하므로 여전히 빠듯합니다

CPU는 오히려 여유롭습니다. 임베딩은 논문 1편 = forward 1회이고, 분석 시간의
대부분은 LLM 응답 대기입니다. **버스터블(t3/t4g) 인스턴스로 충분합니다.**

### 1.3 분석이 `BackgroundTasks`다 — 아키텍처가 반쯤 정해져 있다

[app/routers/submissions.py:142](../app/routers/submissions.py)가
`background_tasks.add_task(run_analysis, ...)`로 분석을 띄웁니다. 작업이 **API 프로세스에
묶여 있다**는 뜻이고, 여기서 세 가지가 따라옵니다.

1. **스케일 투 제로 불가.** Lambda / Cloud Run 스케일-투-제로 계열은 구조상 안 맞습니다.
2. **배포가 진행 중 분석을 죽입니다.** 이미 알고 있는 문제이고 뒷수습 코드가 있습니다 —
   [app/services/analysis.py:34](../app/services/analysis.py)의 `STALE_AFTER = 15분`이
   "재시작으로 영원히 running에 남은 행"을 회수합니다. 정리하지 않으면 그 초안은
   **두 번 다시 분석할 수 없습니다.**
3. → **배포는 한산한 시간에.** 베타 범위에서는 이걸로 충분하다고 판단합니다.

**워커 큐(Celery/RQ)로 빼지 않는 이유:** 브로커 + 워커 프로세스 + 배포 대상이 하나
더 늘어나는데, 동시 분석 1~2건에서 얻는 게 없습니다. 실사용이 쌓여서 "분석 대기가
쌓인다"가 관측되면 그때 근거를 갖고 옮깁니다.

### 1.4 워커를 늘릴 수 없다 (지금은)

rate limit 저장소 기본값이 **프로세스 메모리**입니다. `--workers 4`면 워커마다 따로
세서 실제 상한이 4배가 됩니다. 그 상한들은 장식이 아니라 **LLM 예산의 방어선**입니다:

| 엔드포인트 | 상한 | 위치 |
|---|---|---|
| PDF 업로드 | 20/hour | [submissions.py:43](../app/routers/submissions.py) |
| 분석 시작 | 10/hour | [submissions.py:44](../app/routers/submissions.py) |
| 로그인 | 30/hour | [auth.py:36](../app/routers/auth.py) |
| 가입 | 10/minute | [auth.py:40](../app/routers/auth.py) |

분석 1회가 약 **$0.30**이므로, 상한이 4배가 되면 예산도 4배가 됩니다.

> **결정: `uvicorn --workers 1` 고정.** compose 커맨드에 명시적으로 적습니다.
> 워커를 늘리려면 Redis(`RATE_LIMIT_STORAGE_URI`)가 **먼저** 와야 합니다.

### 1.5 설정이 틀리면 코드가 기동을 거부한다 — 이건 우리 편

`ENVIRONMENT=production`이면 JWT 시크릿·CORS·ALLOWED_HOSTS를 기동 시점에 검사하고
하나라도 어긋나면 서버가 뜨지 않습니다 (README "배포 전 점검").

다만 코드가 **막아주지 못하는** 것 두 가지를 기억해야 합니다.

- **HTTPS 종료는 리버스 프록시의 몫입니다.** 평문 http로 서비스하면서 production으로
  두면 HSTS 헤더가 나가 브라우저가 그 도메인을 https로 기억해 버립니다.
- **`TRUST_PROXY_HEADERS`는 실제 배치와 정확히 맞춰야 합니다.** 프록시 뒤인데 안 켜면
  모든 요청 IP가 프록시 주소라 "로그인 30/hour"가 **전 사용자 합산 30회**가 되고,
  프록시가 없는데 켜면 클라이언트가 `X-Forwarded-For`를 지어내 상한을 우회합니다.
  → 우리 구성은 Caddy 뒤이므로 **`TRUST_PROXY_HEADERS=1`**.

### 1.6 프론트엔드는 반대로 아주 가볍다

AICE-FE는 Vite + React이고 런타임 의존성이 `react` / `react-dom` 둘뿐입니다.
`npm run build` 결과인 `dist/` 정적 파일이면 끝입니다.

## 2. 결정 목록

각 항목은 **결정 / 근거 / 대안을 버린 이유** 순서입니다.

### D1. 단일 EC2 + docker compose (Caddy + API)

**근거.** §1.3 때문에 상시 기동하는 프로세스가 필요하고, §1.2 때문에 메모리가 넉넉해야
합니다. 이 둘을 만족하는 가장 단순한 형태입니다.

**대안을 버린 이유.**
- ECS/Fargate — 오케스트레이션 레이어가 늘어나는데 컨테이너가 2개뿐이라 얻는 게 없음
- Lambda / App Runner 스케일-투-제로 — §1.3과 정면 충돌
- Elastic Beanstalk — 추상화가 문제를 가려서, 뭔가 틀어졌을 때 디버깅이 더 어려움

### D2. 프론트를 **같은 도메인**에서 서빙한다

Caddy가 `/`는 `dist/` 정적 파일, `/api/*`는 uvicorn으로 프록시합니다.

**근거.** 같은 오리진이 되면 **CORS 프리플라이트가 아예 사라지고**, 도메인 1개 ·
인증서 1개로 끝납니다. 배포 시 실수할 수 있는 표면이 통째로 줄어듭니다.

**대안을 버린 이유.** S3 + CloudFront로 쪼개면 도메인 2개, 인증서 2개, CORS 설정,
배포 파이프라인 2개가 됩니다. 베타 트래픽에서 CDN이 주는 이득이 이 복잡도를 못 갚습니다.

> `CORS_ORIGINS`는 그래도 실제 도메인으로 채웁니다 (production 검증을 통과해야 하고,
> 나중에 도메인을 분리할 때 잊지 않기 위해).

### D3. DB는 **RDS PostgreSQL 17** (컨테이너 Postgres 아님)

**근거.**
1. **§0의 "유실은 안 됨"이 핵심.** RDS의 자동 백업 + PITR이 cron `pg_dump` + S3보다
   확실히 낫습니다. 백업 스크립트를 직접 짜고 그게 도는지 감시할 필요가 없습니다.
2. **EBS 볼륨을 날려먹는 최악의 시나리오가 사라집니다.**
3. **`docker-compose.yml`의 `shm_size: 1gb` 해킹이 필요 없어집니다.** 그 설정은 HNSW
   병렬 인덱스 빌드가 기본 `/dev/shm`(64 MB)에서 "could not resize shared memory
   segment"로 죽는 걸 막으려던 것인데, RDS에는 그 문제가 없습니다.
4. 팀에 RDS 운영 경험이 없어서, 통제된 환경에서 한 번 해보는 것 자체가 목적에 포함됩니다.

**연결 코드는 수정이 필요 없다는 것을 확인했습니다.**
[app/database.py:7](../app/database.py)의 `sqlalchemy_url()`은 스킴 접두사만 갈아끼우고
나머지 문자열을 그대로 넘깁니다. 따라서 `?sslmode=require`가 붙은 URL이
SQLAlchemy 쪽과 AI 파트의 psycopg 풀([paper_assistant/db/connection.py:36](../paper_assistant/db/connection.py))
**양쪽 모두** 그대로 통과합니다. RDS는 TLS를 요구하므로 이게 전제 조건이었습니다.

```
DATABASE_URL=postgresql://paper:<비번>@<엔드포인트>:5432/paper_assistant?sslmode=require
```

⚠️ 비밀번호에 `@ : / ? #`가 들어가면 URL 인코딩이 필요합니다. **영숫자로만 만드세요.**

**대안을 버린 이유.** 컨테이너 Postgres는 월 ~$28 쌉니다(§3). 하지만 그 차액을
백업 스크립트 작성 · 복구 검증 · "정말 돌고 있나" 불안으로 지불하게 됩니다.
크레딧이 흡수할 수 있는 금액입니다.

**대신 감수하는 것 (§4.3에 작업으로 반영).**
- VPC / 서브넷 그룹 / 파라미터 그룹 설정 — RDS가 처음이면 여기서 시간이 갑니다
- `scripts/restore_db.sh`가 **RDS에서 동작하지 않습니다** — `docker exec paper-assistant-db`에
  의존합니다. 네트워크 경유 버전을 새로 써야 합니다
- `scripts/init_db.sql`의 자동 실행 훅(`docker-entrypoint-initdb.d`)이 없습니다.
  다만 덤프 복원 경로에서는 어차피 쓰지 않습니다

### D4. 인스턴스 사이징 — EC2 t4g.medium + RDS db.t4g.medium (둘 다 ARM)

| | 사양 | 근거 |
|---|---|---|
| EC2 | t4g.medium (2 vCPU / **4 GB**, **ARM/Graviton**) | DB가 빠져서 API의 2.5 GB(§1.2)만 담으면 됨 |
| RDS | db.t4g.medium (2 vCPU / **4 GB**) | DB 1.45 GB를 캐시에 올리고 작업 메모리 여유 |

**2026-08-08에 t3.medium(x86)에서 t4g.medium(ARM)으로 바꿨습니다.** RAM이 같아서
§1.2의 메모리 계산은 그대로 살아 있고, 값이 월 ~$8 쌉니다.

**코드는 아키텍처를 타지 않습니다.** Dockerfile에 `--platform`이 없고
`FROM python:3.13-slim`이 멀티아치라 **빌드하는 호스트를 그대로 따라갑니다.**
`docker-compose.prod.yml`에도 `platform:` 지정이 없습니다.

유일한 위험 지점은 Dockerfile 1단계가 torch를 PyPI가 아니라 CPU 인덱스에서 받는
것이었는데(`download.pytorch.org/whl/cpu`), 확인해보니 **ARM 휠이 있습니다** —
`torch-2.9.0`~`2.13.0`의 `cp313` `manylinux_2_28_aarch64`. 상한이 걸려 있어 의심스럽던
`bcrypt<4.1`(4.0.1)도 aarch64 abi3 휠이 있고, `psycopg[binary]`·`pymupdf`도 있습니다.

🟡 **다만 ARM에서 빌드해본 적은 없습니다.** §9.3의 검증(이미지 3.67 GB, 오프라인
모델 로드, healthy)은 전부 x86에서 한 것입니다. 휠이 존재한다는 것까지만 확인된
상태이고, **첫 `docker compose build`가 ARM 검증을 겸합니다.**

> RDS가 `db.t4g.medium`(ARM)인 것은 **우리 이미지와 무관합니다.** 앱 컨테이너는
> EC2에서만 돕니다. EC2를 x86으로 두든 ARM으로 두든 RDS는 영향받지 않습니다.

⚠️ **`db.t4g.micro`(1 GB)는 안 됩니다** — 데이터가 1.45 GB입니다. 프리 티어 등급이라
끌리지만 HNSW 검색이 매번 디스크를 칩니다.

⚠️ **Multi-AZ는 켜지 않습니다** — 비용이 2배인데 §0에서 다운타임을 허용했습니다.

### D5. 초대 게이트는 **가입 자체를 잠그는 방식**(A안)

`SIGNUP_INVITE_CODE` 환경변수 하나. 코드를 모르면 계정이 안 만들어지고,
LLM에 돈이 걸린 경로(`POST /submissions/{id}/analysis`, `GET /papers/{id}/story?refresh=true`)는
전부 로그인 뒤에 있으므로 **로그인한 사람 = 초대된 사람**이 성립합니다.

🔴 **반드시 두 경로를 모두 막아야 합니다.**
[app/routers/auth.py:141](../app/routers/auth.py)의 구글 로그인이 **처음 보는 계정을
자동 생성**합니다. `/signup`만 막으면 구글 버튼으로 그대로 뚫립니다.

**대안(B안: 사용자별 LLM 플래그)을 버린 이유.** `users`에 권한 컬럼이 없어
([app/models/user.py](../app/models/user.py)) 마이그레이션이 필요하고, 관리 UI가 없어
결국 수동 SQL로 켜고 끄게 됩니다. 베타 규모에서 정밀도를 얻는 값이 너무 비쌉니다.
초대 인원이 늘어 "이 사람만 LLM 끄고 싶다"가 실제로 생기면 그때 B로 갑니다.

### D6. LLM은 켠다 (`PAPER_ASSISTANT_USE_LLM=1`)

D5의 초대 게이트가 예산을 초대 인원으로 묶어준다는 전제 위에서만 켭니다.

- 분석 1회 ≈ **$0.30** (Sonnet 5, 26페이지 PDF 기준. 2026-08-31까지 도입가, 이후 ~1.5배)
- **AWS 크레딧과 무관합니다** — Anthropic 쪽에서 따로 청구됩니다
- Anthropic 콘솔에도 예산 알림을 걸어둡니다

### D7. `WARMUP_ON_STARTUP=1`

SPECTER2 로드(수십 초)를 첫 사용자 요청이 아니라 기동 시점으로 옮깁니다. 배포마다
기동이 느려지지만, 베타 사용자가 첫 분석에서 수십 초를 기다리는 것보다 낫습니다.

### D8. `ENABLE_DOCS=0`

production에서는 명시하지 않아도 자동으로 닫히지만, **의도임을 드러내기 위해**
`.env`에 적습니다. 나중에 누가 "왜 /docs가 안 열리지"로 헤매지 않도록.

### D9. 도메인과 DNS는 **Cloudflare** (Route 53 아님)

**근거.** 등록비가 원가(~$10/년)라 더 싸고, §3.1의 AWS 크레딧 예외를 통째로 비켜갑니다.
DNS도 Cloudflare에 두면 Route 53 호스팅 영역 $0.50/월도 나가지 않습니다. DNS는 어디에
두든 하는 일이 같아서, AWS 안에 둘 이유가 이 항목에는 없습니다.

⚠️ **Cloudflare Registrar는 Cloudflare 네임서버 사용이 조건입니다** — 여기서 등록하면서
DNS만 Route 53에 두는 선택지는 사실상 없습니다. 등록 화면에서 확인하세요.

⚠️ **지원하지 않는 TLD가 있습니다** (`.kr` 등). `.com` / `.dev` / `.io`는 됩니다.

🔴 **DNS 레코드를 "DNS only"(회색 구름)로 둘 것. 프록시(주황 구름)를 켜면 안 됩니다.**

이게 이 결정에서 유일하게 위험한 지점입니다. Cloudflare는 A 레코드를 만들 때 **기본이
프록시 켜짐**이라, 아무 생각 없이 넘어가면 이 상태가 됩니다.

- **Caddy의 인증서 발급이 막힙니다.** 프록시가 켜지면 Cloudflare가 엣지에서 TLS를
  종료하고 자기 인증서를 씁니다. Caddy는 Let's Encrypt 인증서를 **직접** 받아야 하는데,
  SSL 모드가 Full(strict)이면 오리진에 유효한 인증서가 이미 있어야 통과합니다 —
  그 인증서를 받으려고 발급을 시도하는 중이므로 닭과 달걀이 됩니다.
- **§1.5의 프록시 추론이 흐트러집니다.** 프록시 홉이 하나 더 생겨
  `X-Forwarded-For`에 Cloudflare가 끼어듭니다. 회색 구름이면 프록시는 Caddy 하나뿐이라
  `TRUST_PROXY_HEADERS=1`의 근거가 그대로 성립합니다.

**대안(프록시를 켜는 것)을 버린 이유.** 오리진 IP 은닉과 무료 DDoS 방어를 얻지만,
Cloudflare Origin Certificate를 Caddy에 심고 SSL 모드를 맞추는 설정이 늘어납니다.
베타 규모에서 필요하지 않고, **나중에 켜고 싶으면 그때 전환하면 됩니다** — 회색 구름으로
시작하는 것이 되돌리기 쉬운 방향입니다.

> 참고: Cloudflare 무료 플랜에는 요청 본문 100 MB 상한이 있지만, 우리 상한은
> `MAX_REQUEST_BYTES` 24 MB라 프록시를 켜더라도 걸리지 않습니다.

## 5. 만들어야 할 것

착수 시점에 저장소에 **없던** 것들입니다 (README "배포 설정(Dockerfile 등)은 없습니다").

> ✅ **§5.1·§5.2·§5.3은 전부 만들어졌습니다.** 남은 것은 `requirements.lock.txt`
> 하나뿐이고, §5.4의 운영 절차는 §9.9(배포/롤백)와 §9.5-⑪(복구 리허설)로 옮겨졌습니다.
> 아래는 무엇을 왜 그렇게 만들었는지의 근거로 남깁니다.

### 5.1 배포 파일

| # | 파일 | 핵심 |
|---|---|---|
| 1 | `Dockerfile` | torch **CPU 휠을 먼저** 설치 (순서 바꾸면 수 GB CUDA 빌드를 받음). SPECTER2 가중치를 **이미지에 구워넣기** |
| 2 | `docker-compose.prod.yml` | `api` + `caddy`. `--workers 1` 명시, 메모리 제한, `restart: unless-stopped` |
| 3 | `Caddyfile` | TLS 자동, `/api/*` 프록시, `/`는 `dist/`, `X-Forwarded-For` 전달 |
| 4 | `.env.production.example` | 아래 §5.2 |

**왜 모델 가중치를 이미지에 굽는가.** 안 그러면 기동할 때마다 Hugging Face에서 수백 MB를
받습니다 — 이미지가 커지는 대신 (a) 기동이 빨라지고 (b) **HF 장애가 우리 장애가 되지
않습니다.** 이미지는 4~5 GB가 되지만, EC2에서 직접 빌드하면 레지스트리(ECR)도 필요 없고
그 비용도 안 듭니다.

🔴 **락파일이 필요합니다.** `requirements.txt`는 의도적으로 하한(`>=`)만 씁니다 —
버전 고정이 오히려 환경을 깨뜨린 적이 있어서입니다(파일 상단 주석). 로컬 개발에는 맞는
선택이지만 **배포 이미지에는 맞지 않습니다.** 언제 빌드하느냐에 따라 다른 버전이 들어가서,
"어제 되던 이미지가 오늘 안 된다"를 재현할 수 없게 됩니다.

이게 가설이 아니라는 걸 CI에서 확인했습니다. `requirements.txt`는 `transformers>=4.57`로
**상한이 없는데**, SPECTER2를 로드하는 `adapters 1.3.0`은 `transformers ~=4.57.6`으로
고정합니다. 지금은 pip가 adapters의 핀을 보고 4.57.x로 되돌리지만, 이건 **의존성 해석에
운을 맡기는 것**입니다. 배포에서는 `pip freeze`로 뜬 락파일을 이미지에 넣습니다.

```bash
pip freeze > requirements.lock.txt   # 검증된 환경에서 한 번 뜨고, 이미지는 이것만 본다
```

### 5.2 프로덕션 환경변수


이 목록은 착수 시점 기준입니다. **비밀번호 재설정 메일이 들어오면서 SMTP 키 6개가

`SMTP_FROM`이라는 것이 거기서 가장 중요한 함정입니다.

🔴 `JWT_SECRET_KEY`는 **반드시 새로 생성**합니다. 개발용 값을 그대로 쓰면 공격자가
임의 `user_id`로 토큰을 위조해 아무 계정으로나 로그인할 수 있고, 서버는 그걸 정상

## 7. 열린 위험

정직하게 적어둡니다.

- 🔴 **배포가 진행 중 분석을 죽입니다** (§1.3). `STALE_AFTER=15분`이 DB 행은 회수하지만
  **사용자는 실패를 봅니다.** 베타에서 이게 자주 걸리면 워커 큐 분리를 앞당깁니다.
- 🟡 **DB가 사용자 활동만큼 계속 큽니다** (§1.1, PDF가 BYTEA). RDS 스토리지 사용량을
  주기적으로 봐야 합니다. 스토리지 자동 확장을 켜두면 조용히 비용이 오릅니다 —
  **알림을 먼저 걸고 켜세요.**
- 🟡 **런웨이 ~1.9개월**(§3). 베타가 길어지면 RDS를 컨테이너 Postgres로 되돌리거나
  인스턴스를 줄여야 합니다. **크레딧 잔액을 주 1회 확인.**
  최근 확인: **$130+ / 2026-08-10** (배포일 2026-08-08에는 $140+)
- 🔴 **백업이 아직 검증되지 않았습니다.** 자동 백업은 돌지만 스냅샷에서 복원을 한 번도
  해보지 않았습니다 (§9.5-⑪). §0의 "유실은 안 됨"이 지금은 **가정**입니다.
  **실사용자를 받기 전에 닫아야 하는 위험입니다**
- 🟡 **분석 1건은 성공했지만 수치를 안 남겼습니다** (§9 상단). 실제 LLM 비용이 §3의
  $0.30 가정과 맞는지, 분석 중 메모리가 §1.2의 미지수(스캔본 렌더링)를 건드리는지
  둘 다 여전히 모릅니다. **다음 분석에서 반드시 재세요**
- 🟡 **배포 이미지에 알려진 CVE가 들어갑니다.** `transformers 4.57.6`에 4건
  (PYSEC-2025-217 / 2026-2288 / 2026-2289 / 2026-2290)이 있고 **fix가 전부
  transformers 5.x인데, `adapters 1.3.0`이 `transformers ~=4.57.6`으로 고정해 올릴 수가

#### `requirements.lock.txt` — 지금 뜨는 것이 가장 쉽습니다

원래 계획은 "검증된 이미지에서 `pip freeze`"였고, 한동안은 그 이미지가 이전 PC에만
있어서 막혀 있었습니다. **이제는 아닙니다 — EC2에서 실제로 돌고 있는 컨테이너가
바로 그 검증된 환경입니다.** 서버에서 한 줄이면 끝납니다.

```bash
docker compose -f docker-compose.prod.yml exec api pip freeze > requirements.lock.txt
```

**미루면 비싸집니다.** 지금 도는 컨테이너를 재빌드하는 순간 이 조합은 사라지고,
그때는 "어제 되던 이미지"를 재현할 방법이 없습니다. 락파일이 잡아두려는 것이
정확히 그 조합입니다 (§5.1의 `transformers` / `adapters` 핀 충돌 참고).

> 락파일을 쓸 때 주의: 락에 `torch==2.13.0+cpu`가 들어갑니다. PyPI에는
> 없는 버전이므로 **Dockerfile의 2단계 구조(CPU 인덱스에서 torch 먼저)를 유지해야**

#### `maintenance_work_mem`을 파라미터 그룹이 아니라 **role에 거는 이유**

HNSW 인덱스 재빌드는 이 값이 낮으면 하염없이 느립니다. 그래서 복원 전에 올려야
하는데, **`paperai-pg17`에 박아두면 안 됩니다.**

`autovacuum_work_mem`의 기본값은 `-1`이고, 그것은 **"`maintenance_work_mem`을 그대로
쓴다"**는 뜻입니다. autovacuum 워커는 기본 3개까지 뜨므로, 파라미터 그룹에 2 GB를
넣어두면 4 GB짜리 db.t4g.medium이 최악의 경우 3 × 2 GB를 감당해야 합니다. 복원은
한 번뿐인데 위험은 상시로 남습니다.

대신 **복원에 쓰는 role에만** 겁니다. autovacuum 워커는 로그인 role이 아니라서 이
설정을 물려받지 않습니다 — 위험이 복원 세션 안에만 머뭅니다.

```sql
-- 복원 직전
ALTER ROLE paper SET maintenance_work_mem = '512MB';
ALTER ROLE paper SET max_parallel_maintenance_workers = 0;   -- 아래 이유

-- 복원이 끝난 뒤 (잊지 말 것)
ALTER ROLE paper RESET maintenance_work_mem;
ALTER ROLE paper RESET max_parallel_maintenance_workers;
```

`maintenance_work_mem`은 동적 파라미터라 **재부팅이 필요 없고**, 새로 맺는 세션부터
적용됩니다(`pg_restore`가 여는 연결 포함).

⚠️ **`pg_restore --jobs N`과 곱해집니다.** 병렬 작업 하나하나가 별도 연결이라 각자
이만큼을 잡을 수 있습니다. 4 GB 인스턴스에서 `512MB` × `--jobs 2` = 1 GB가 적당합니다.

#### 🔴 병렬 HNSW 빌드는 그 메모리를 **공유 메모리**에서 가져간다

**1 GB로 잡았다가 리허설에서 실제로 밟은 것입니다.** 값을 내린 진짜 이유입니다.

```
pg_restore: error: could not execute query: ERROR:  could not resize shared memory
segment "/PostgreSQL.1507269598" to 1070632832 bytes: No space left on device
Command was: CREATE INDEX papers_embedding_hnsw ON public.papers USING hnsw (...)
```

디스크가 아니라 **`/dev/shm`이 모자라다**는 뜻입니다. pgvector의 *병렬* HNSW 빌드는
`maintenance_work_mem`만큼을 프로세스 private 메모리가 아니라 **동적 공유 메모리**에
잡습니다. 그래서 이 값은 "RAM에 여유가 있는가"가 아니라 **"공유 메모리에 들어가는가"**로
따져야 합니다.

`max_parallel_maintenance_workers = 0`이면 그 경로를 아예 타지 않고 private 메모리에서
빌드합니다. **잃는 것이 거의 없습니다** — `papers_embedding_hnsw`는 **169 MB**짜리고,
43,515행이라 직렬로도 몇 분입니다. 4 GB 인스턴스에서 병렬화는 속도를 조금 얻자고
OOM 위험을 사는 거래입니다.

같은 이유로 **로컬에서 컨테이너에 복원할 때는 `--shm-size`를 올려야 합니다**(도커
기본값이 64 MB입니다). 리허설에서는 워커를 0으로 두고 기본 64 MB 그대로 통과했습니다.

### 9.6 잊으면 안 되는 함정

작업 중 **실제로 밟았던 것들**입니다. 전부 조용히 실패하는 종류입니다.

- 🔴 **Cloudflare는 회색 구름(DNS only)을 유지.** 주황 구름을 켜면 (a) Caddy가 인증서를
  못 받고 (b) `X-Forwarded-For` 홉이 하나 늘어 **전 사용자가 rate limit 바구니 하나를
  공유**합니다 (로그인 30/hour → 서비스 전체 30회). D9 참고
- 🔴 **프론트를 `VITE_API_BASE_URL` 없이 빌드하면 화면 전체가 mock으로 동작**합니다.
  가입·로그인·분석이 전부 가짜로 "성공"하고 백엔드는 조용합니다. 이제 빌드 가드가
  막지만, **배포된 번들 검증은 `grep -c mock dist/assets/*.js`가 0인지로** 합니다
  (올바르게 빌드하면 minifier가 mock 경로를 통째로 제거합니다)
- 🔴 **`docker compose down -v`를 쓰지 마세요.** `caddy_data` 볼륨에 TLS 인증서가
  있습니다. 날리면 재발급인데 Let's Encrypt에 발급 상한이 있습니다
- 🟡 **`ALLOWED_HOSTS`에서 `localhost`를 빼지 마세요.** 헬스체크가 400을 맞고
  컨테이너가 영원히 unhealthy가 됩니다 — 배포 자동화가 멀쩡한 컨테이너를 죽입니다
- 🟡 **`.dockerignore`는 줄 끝 주석을 지원하지 않고, `*`는 `/`를 넘지 않습니다.**
  이것 때문에 코퍼스 덤프 459 MB가 이미지에 들어갔었습니다. 규칙을 고친 뒤에는
  빌드 로그의 `transferring context:` 크기로 확인하세요
- 🔴 **DB 덤프는 코퍼스만이 아닙니다.** 전체 DB 덤프라 `users`·`submissions`(PDF 원본
  포함)가 함께 들어 있습니다. 그대로 복원하면 **초대 게이트를 통과한 적 없는 계정이
  프로덕션에 생깁니다.** 반드시 §9.5-⑤의 `--exclude-table-data`로 새로 뜨고,
  복원 후 `users`·`submissions` 건수가 0인지 확인하세요
- 🟡 **덤프를 뜰 수 있는 PC가 한정됩니다.** 코퍼스는 git에 없으므로(`data/`가
  `.gitignore`) 로컬 DB가 적재된 컴퓨터에서만 덤프를 만들 수 있습니다. 작업 PC를
  옮길 때 이걸 먼저 확인하세요
- 🔴 **보내는 주소 키는 `SMTP_FROM`입니다. `MAIL_FROM`이 아닙니다.** `config.py`가
  `extra="ignore"`라 이름을 틀리면 **아무 말 없이 무시**되고, SMTP를 전부 채워두고도
  발송 조건(HOST와 FROM 둘 다)이 불성립이라 재설정 메일이 한 통도 안 나갑니다.
  지금은 기동 검증이 이 경우를 막습니다 (§9.8)
- 🟡 **Caddyfile에 선언한 도메인은 전부 DNS가 먼저 있어야 합니다.** `www` 레코드
  없이 www 블록을 둔 채 기동해서 인증서 검증이 NXDOMAIN으로 반복 실패했습니다.
  apex는 정상 발급돼 사이트는 떴지만(발급이 통째로 막히지는 않았습니다),
  **실패한 검증도 Let's Encrypt 한도에 잡힙니다.** 순서는 DNS 먼저, Caddy 나중.
  이미 백오프가 걸렸으면 `docker compose restart caddy`로 즉시 재시도시킵니다.
  → **해결:** Cloudflare에 `www` 레코드를 추가해서 지금은 둘 다 발급됩니다 (§9.1)
- 🟡 **`/docs`가 200이어도 놀라지 마세요.** Caddy가 `/api/*`만 백엔드로 보내고
  나머지는 SPA로 폴백하므로, `/docs`는 프론트 index.html입니다. FastAPI 문서가
  닫혔는지는 **`/api/docs`로** 확인해야 합니다
- 🔴 **병렬 HNSW 빌드는 `maintenance_work_mem`을 `/dev/shm`에서 가져갑니다.** 값을
  넉넉히 준 것이 오히려 복원을 죽입니다(`could not resize shared memory segment`).
  `max_parallel_maintenance_workers = 0`으로 피합니다 — §9.5-④ 참고
- 🟡 **배포는 한산한 시간에.** 분석이 `BackgroundTasks`라 재시작이 진행 중 작업을
  죽입니다 (§1.3)

### 9.8 비밀번호 재설정 메일 (SES SMTP) — 2026-08-09

팀원이 재설정 코드를 넣었고 SES SMTP 설정이 끝났습니다. 배포에 반영하면서 확인한 것.

**현재 상태 (2026-08-10).** 서버 `.env.production`에 아래 키를 **전부 채웠고** 기동
검증도 통과했습니다. 🟡 **하지만 메일이 실제로 도착하는지는 아직 확인하지
않았습니다** — 아래 "발송 실패는 사용자에게 알리지 않는다" 설계 때문에,
안 해보면 알 수 없습니다.

**환경변수 이름 — `MAIL_FROM`이 아니라 `SMTP_FROM`입니다.**

```
SMTP_HOST=email-smtp.ap-northeast-2.amazonaws.com
SMTP_PORT=587                      # 587=STARTTLS, 465=SSL (코드가 포트로 자동 판별)
SMTP_USER=<SES SMTP 자격증명>       # ⚠️ IAM 액세스 키와 다른 값이다
SMTP_PASSWORD=<SES SMTP 자격증명>
SMTP_FROM=noreply@paperaireview.com # ⚠️ MAIL_FROM 아님. SES에서 검증한 주소여야 함
FRONTEND_BASE_URL=https://paperaireview.com   # 끝 슬래시는 있어도 없어도 됨
```

`FRONTEND_BASE_URL`은 `build_reset_url`이 `rstrip("/")`하므로 어느 쪽이든 같습니다.
링크는 `{base}/reset-password?token=...` 꼴로 만들어집니다.

**기동 검증에 넣은 것과 넣지 않은 것.** 메일이 **아예 없는 것**은 기동을 막지
않습니다 — CORS·ALLOWED_HOSTS는 틀리면 공개되고 초대 코드는 틀리면 청구되지만,
SMTP가 빈 것은 기능 하나가 꺼진 상태이고 이미 시끄럽게 실패합니다(production이면
`/password/forgot`이 503). 그것 때문에 분석·검색까지 내리는 것은 손해가 큽니다.

**절반만 채운 설정은 막습니다.** 이쪽이 진짜 조용한 실패입니다.

| 상황 | 결과 |
|---|---|
| 메일 전혀 미설정 | 기동함 (기능만 꺼짐, 요청 시 503) |
| `MAIL_FROM`으로 잘못 씀 → `SMTP_FROM` 누락 | **기동 거부** |
| `SMTP_USER`만 있고 `SMTP_PASSWORD` 없음 | **기동 거부** |
| 메일은 켰는데 `FRONTEND_BASE_URL`이 localhost | **기동 거부** |

🔴 **발송 실패는 재시도하지 않고, 사용자에게도 알리지 않습니다.** 일부러 그렇게
돼 있습니다 — 실패를 사용자에게 돌려주면 "실패했다 = 그 계정이 존재한다"가 되어
계정 존재 여부를 숨기려는 설계가 깨집니다. 대신 `log.exception`으로 스택까지
남깁니다. **그래서 발송 실패는 로그로만 알 수 있습니다.**

🔴 **바운스는 앱 로그에 절대 안 나옵니다.** SES는 일단 250으로 받아들이고 나중에
비동기로 반송하므로, `_send`는 성공으로 끝납니다. 평판 관리는 **SES 쪽에서**
해야 합니다 — 바운스/불만 SNS 토픽을 걸고 CloudWatch에서 바운스율을 보세요.
SES 기준은 바운스 5%·불만 0.1%이고, 넘으면 계정이 정지될 수 있습니다.

⚠️ **SES는 아직 샌드박스입니다 — 프로덕션 액세스는 신청했고 심사 대기 중입니다**
(2026-08-10). 승인 전까지는 검증된 주소로만 나가고, 베타 테스터 이메일이 검증돼
있지 않으면 **발송이 실패하는데 사용자에게는 200이 나갑니다**(위 설계).
**승인이 떨어지기 전까지는 재설정 기능을 안내하지 마세요.**

🔴 **프론트에 `/reset-password` 화면이 없습니다.** 메일은 나가지만 링크를 눌러도
아무 일도 일어나지 않습니다 — AICE-FE는 라우터 없이 `useState('landing')`으로만
화면을 바꿔서 **URL과 토큰을 아무도 읽지 않습니다.** Caddy가 SPA 폴백으로
index.html을 주고 랜딩 화면이 뜹니다. 백엔드는 완성됐고 **프론트 작업이
남았습니다 — 팀원이 맡았습니다.**

> 정리하면 재설정 기능이 실제로 쓰이려면 **세 가지가 다 필요합니다**:
> ① SES 프로덕션 액세스 승인 · ② 프론트 `/reset-password` 화면 · ③ 실제 수신 확인.
> 지금은 셋 다 미완이므로 **기능이 있는 것처럼 안내하면 안 됩니다.**

메일 본문에는 회신 불가 안내를 넣었습니다(`noreply@`에 수신 MX가 없습니다).
문의처 주소는 **실제로 사람이 읽는 주소가 정해지면** 넣기로 하고 비워 두었습니다 —
닿지 않는 주소를 적는 것은 안 적는 것보다 나쁩니다.

### 9.9 배포와 롤백 — 실제로 쓰는 명령

§5.4-8이 미뤄뒀던 절차입니다. 처음 배포하며 실제로 쓴 것만 적습니다.

**배포.** 🟡 **한산한 시간에 하세요** — 재시작이 진행 중 분석을 죽입니다 (§1.3).

```bash
ssh -i ~/paperai-key.pem ubuntu@paperaireview.com
cd ~/AICE-BE && git pull
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps      # api가 healthy 인지
docker compose -f docker-compose.prod.yml logs -f api
```

기동은 §1.5의 검증을 통과해야 시작됩니다. **설정이 틀리면 컨테이너가 뜨지 않고
멈추므로**, `ps`에서 `healthy`를 확인하기 전까지는 배포가 끝난 게 아닙니다.
`WARMUP_ON_STARTUP=1`이라 SPECTER2 로드에 수십 초 걸립니다 (D7).

**프론트만 바뀐 경우**는 재빌드가 필요 없습니다. 로컬에서 빌드해 올리면 끝입니다
(빌드 명령과 함정은 §9.5-⑧).

```bash
rsync -av --delete -e "ssh -i ~/paperai-key.pem" \
  dist/ ubuntu@paperaireview.com:~/AICE-BE/frontend-dist/
```

**롤백.** 이전 커밋으로 되돌려 다시 빌드합니다.

```bash
git log --oneline -5          # 돌아갈 커밋 확인
git checkout <이전 커밋>
docker compose -f docker-compose.prod.yml up -d --build
```

🔴 **`docker compose down -v`는 절대 쓰지 마세요.** `caddy_data` 볼륨의 TLS 인증서가
날아가고, Let's Encrypt에는 발급 상한이 있습니다 (§9.6). 컨테이너만 내리려면
`down`까지만 씁니다.

⚠️ **DB 마이그레이션이 낀 배포는 코드만 되돌린다고 롤백되지 않습니다.**
`alembic upgrade`가 스키마를 이미 바꿔놨다면 `alembic downgrade`가 따로 필요하고,
데이터를 지우는 마이그레이션이면 그것도 안 됩니다. 그런 배포 전에는 **RDS
스냅샷을 수동으로 하나 떠두세요** — 자동 백업과 별개로, 되돌릴 지점이 명확해집니다.
