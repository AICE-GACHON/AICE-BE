# ML/AI 논문 리서치 어시스턴트 — 기획 문서

## 1. 프로젝트 개요

**한 줄 소개**
ML/AI 분야 연구자를 위한 RAG 기반 웹 서비스. 유사 논문을 검색하고, 해당 논문들의 실제 리뷰(피어리뷰) 히스토리를 보여주며, 유사한 연구가 어떤 학회/저널에 게재되는 경향이 있는지를 데이터로 알려준다.

**핵심 가치 제안**
"내 논문과 비슷한 연구들이 어디서, 어떤 피드백을 받고, 어디에 붙었는가"를 한 곳에서 확인할 수 있게 한다.

---

## 2. 문제 정의

연구자들이 논문을 쓰거나 투고를 준비할 때 반복적으로 겪는 어려움:

- **유사 연구 파악의 어려움**: 키워드 검색만으로는 방법론·데이터셋·문제 설정이 실제로 얼마나 유사한지 알기 어려움
- **리뷰 히스토리의 불투명성**: 비슷한 논문이 어떤 지적을 받고 통과/거절되었는지 알 수 없어 자기 논문의 약점을 예측하기 어려움
- **투고처 선정의 비효율**: 임팩트팩터나 명성만으로 투고처를 고르고, 실제 해당 학회/저널이 이 유형의 논문을 얼마나 잘 받아주는지에 대한 정보가 부족함

기존 도구(Connected Papers, Elicit, Semantic Scholar 등)는 1번 기능 위주이며, 2·3번을 결합해 인사이트를 주는 서비스는 아직 부재.

---

## 3. 타겟 사용자

- ML/AI 분야 대학원생 (석·박사 과정, 특히 첫 투고를 준비하는 연구자)
- 논문 리비전을 준비 중인 저자
- 랩(연구실) 단위로 투고 전략을 세우는 지도교수/시니어 연구자

---

## 4. 핵심 기능

### 4.1 유사 논문 검색 (RAG 기반)
- 사용자가 초록/키워드/자신의 draft를 입력하면 임베딩 기반으로 유사 논문 검색
- 단순 유사도 점수가 아니라 **유사성의 근거를 구조화**해서 제시
  - 방법론 유사 / 데이터셋 겹침 / 문제 설정 유사 / 인용 관계 등으로 태깅
- 데이터 소스: arXiv, Semantic Scholar API

### 4.2 리뷰·피드백 히스토리 조회
- 검색된 유사 논문들의 실제 피어리뷰, 메타리뷰, 저자-리뷰어 논쟁(rebuttal) 내용을 가져와 요약
- 반복적으로 등장하는 지적 패턴을 클러스터링해서 제시
  - 예: "유사 논문 10편 중 6편이 '실험 규모 부족' 지적을 받음"
- 데이터 소스: OpenReview API (ICLR, NeurIPS, ICML, COLM 등)

### 4.3 게재 저널/학회 경향 분석
- 유사 논문들이 실제로 어느 학회/저널에 최종 게재되었는지 집계
- 단순 리스트가 아니라 **행동 데이터 기반 인사이트** 제공
  - 예: 이 유형 논문의 학회별 accept 경향, reject 후 재투고 패턴(ICLR reject → NeurIPS accept 등)
- 데이터 소스: OpenReview 게재 정보 + Semantic Scholar venue 메타데이터

---

## 5. 차별화 포인트

| 항목 | 기존 도구 | 본 서비스 |
|---|---|---|
| 유사 논문 검색 | 있음 (Connected Papers, Elicit) | 있음 + 유사성 근거 구조화 |
| 리뷰 히스토리 | 없음 | OpenReview 기반 실제 리뷰 요약·패턴 클러스터링 |
| 투고처 추천 | 저널 매칭 툴 존재 (JANE 등, 범용 학문 분야) | ML/AI 특화 + 실제 accept/reject 행동 데이터 기반 |

**분야를 ML/AI로 좁힌 이유**: OpenReview가 리뷰·메타리뷰·rebuttal을 전부 공개하는 사실상 유일한 대규모 데이터 소스이기 때문. 범용 학문 분야로 확장 시 리뷰 데이터 자체가 존재하지 않아 2번 기능이 성립하지 않음.

---

## 6. 데이터 소스 및 기술 스택 (초안)

**데이터 소스**
- OpenReview: venue×연도 단위로 논문 본문, 리뷰, 메타리뷰, rebuttal, decision 수집 (핵심 데이터 소스)
- Semantic Scholar: 여기서 부족한 부분을 보강 — 논문 메타데이터, 인용 관계, 저자 ID, venue 정보
- arXiv: arXiv ID 매칭, 초록/카테고리 보강

**기술 스택 (제안)**
- 임베딩/검색: 논문 임베딩(예: SPECTER2 등 학술 특화 임베딩) + 벡터 DB (Pinecone, Weaviate, pgvector 등)
- 백엔드: RAG 파이프라인 (LLM으로 리뷰 요약·패턴 클러스터링)
- 프론트엔드: 검색 → 유사 논문 리스트 → 논문별 리뷰 히스토리/게재 경향 상세 뷰

*(기술 스택은 다음 단계에서 세부 확정 필요)*

---

## 7. MVP 범위

**포함 (In)**
- ICLR / NeurIPS 두 학회로 한정한 유사 논문 검색
- 해당 논문들의 OpenReview 리뷰 요약 (사람이 읽기 쉬운 형태로 정리)
- 유사 논문 게재 학회 통계 (accept rate, 재투고 흐름 간단 집계)

**제외 (Out, 향후 확장)**
- ICML, COLM 등 타 학회 확장
- 사용자 자신의 draft 업로드 후 "예상 지적사항" 예측 기능
- 투고처 추천 랭킹 알고리즘 고도화
- 협업/팀 단위 기능 (랩 공유, 코멘트)

---

## 8. 향후 로드맵 (제안)

1. **Phase 1 (MVP)**: ICLR/NeurIPS 한정, 3대 핵심 기능 최소 구현
2. **Phase 2**: 커버리지 확장 (ICML, ACL, COLM 등), 리뷰 패턴 클러스터링 고도화
3. **Phase 3**: 사용자 draft 기반 "예상 리뷰 지적" 예측, 투고처 추천 랭킹
4. **Phase 4**: 범용 학문 분야 확장 검토 (단, 오픈리뷰 데이터 존재 여부에 따라 기능 축소 필요)

---

## 9. 리스크 및 고려사항

- **데이터 커버리지 한계**: OpenReview에 없는 학회/저널(대부분의 전통 저널)은 리뷰 히스토리 기능이 작동 안 함 → MVP 단계에서 명확히 커뮤니케이션 필요
- **저작권/이용 약관**: OpenReview, Semantic Scholar 등 API 이용 약관 확인 필요 (상업적 이용 가능 여부)
- **리뷰 요약의 정확성**: LLM 기반 요약이 리뷰의 뉘앙스를 왜곡하지 않도록 검증 프로세스 필요
- **경쟁 리스크**: Semantic Scholar, OpenReview 자체가 유사 기능을 추가할 가능성
